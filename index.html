Git & GitHub Guidelines

How the Synapse team branches, commits, reviews, and ships. Every repo follows these rules. GitHub enforces most of them, so treat this page as an explanation of why the guardrails exist and how to work with them.

v1.0Effective 2026-10-07 (UTC)Model: Git Flow liteMerge: merge commits

Golden rules

If you only read one section, read this one.

  1. Nobody pushes directly to main or develop, including admins. Every change goes through a pull request.
  2. A PR can merge only when CI is green, it has the required approvals (1 into develop, 2 into main), a code owner approved it, and every review conversation is resolved.
  3. Branch from develop. The only exception is hotfix/*, which branches from main.
  4. Every commit follows Conventional Commits. commitlint enforces this on your machine and again in CI.
  5. PRs merge with a merge commit, so every commit on your branch ends up in shared history. Tidy your commits before you ask for review.
  6. Keep PRs small: aim for under 400 changed lines and one concern per PR.
  7. Versions, tags, and the changelog come from release-please. Never bump a version or create a tag by hand.
  8. Secrets never go into git. If one leaks, rotate it first and clean up history second.

Branch model

We use Git Flow lite: two long-lived branches, short-lived work branches, and no release/* branches. To ship a release, open a PR from develop into main.

BranchPurposeEnvironmentDeploys when
mainProduction code. Every commit on main has been released or is about to be.ProductionA release-please Release PR is merged, which creates tag vX.Y.Z. The deploy also waits for approval on the production environment.
developIntegration branch. Must always be deployable.StagingAny PR merges into develop.
feature/* …Short-lived work branches.None (preview optional)Never.
hotfix/*Urgent fix for production.NoneThrough main once merged.
Tip: make develop the default branch on GitHub. New PRs then target it automatically, and nobody opens a feature PR into main by mistake.

Branch naming

Format: type/short-description. Use lowercase kebab-case, at most 40 characters after the slash. Name the change, not the person who made it. Link the issue in the PR description (Closes #123), not in the branch name.

PrefixUse forFromIntoExample
feature/New functionalitydevelopdevelopfeature/jwks-rotation
bugfix/A non-urgent bug found on develop or stagingdevelopdevelopbugfix/null-token-refresh
hotfix/An urgent production bugmainmain, then back-merged into develophotfix/login-500
refactor/Code changes with no change in behaviordevelopdeveloprefactor/split-token-service
chore/Tooling, dependencies, configdevelopdevelopchore/node-24-upgrade
docs/Documentation onlydevelopdevelopdocs/auth-flow-diagram

Validation regex, if you want CI to check branch names:

^(feature|bugfix|hotfix|refactor|chore|docs)/[a-z0-9]+(-[a-z0-9]+)*$

Branches named release-please--* belong to the release bot. Don't commit to them.

Commit messages

We follow Conventional Commits 1.0. release-please reads these messages to pick the next version and write the changelog, so a wrong type means a wrong release.

<type>(<scope>): <subject>

<body: what changed and why, wrapped at 100 chars>

<footer: BREAKING CHANGE: …, Refs #123>
TypeUse whenVersion effect
featAdds a user-facing capabilityminor · 1.4.0
fixFixes a bugpatch · 1.4.1
perfMakes something faster with no change in behaviorpatch
refactorRestructures code with no change in behaviornone
testAdds or fixes tests onlynone
docsChanges documentation onlynone
buildBuild system or dependenciesnone
ciCI workflowsnone
choreMaintenance that matches no other typenone
styleFormatting onlynone
revertReverts an earlier commitdepends on the reverted commit
feat! / BREAKING CHANGE:Breaks an API, config, or schema contractmajor · 2.0.0

Rules

  • Write the subject in the imperative mood, start it lowercase, and leave off the final period: add, not added or adds.
  • Keep the header to 72 characters or fewer.
  • The scope is the module or package, in kebab-case: auth, gateway, admin-ui, deps.
  • Each commit holds one logical change, and the code builds and passes tests at every commit so git bisect keeps working.
  • The body explains why. The diff already shows what.
  • Commits like wip, fix, or review changes never reach a shared branch. Squash them locally before review (see Daily workflow).

Good

  • feat(auth): add JWKS endpoint with key rotation
  • fix(gateway): return 401 when token kid is unknown
  • perf(events): batch PII redaction per request
  • feat(api)!: drop v1 session endpoints

Bad

  • Fixed stuff
  • feat: Added new feature.
  • update auth + gateway + ui changes
  • wip

Enforcement

export default {
  extends: ['@commitlint/config-conventional'],
  rules: {
    'header-max-length': [2, 'always', 72],
    'scope-case': [2, 'always', 'kebab-case'],
  },
};
one-time setup per repo
npm i -D @commitlint/cli @commitlint/config-conventional husky
npx husky init
echo 'npx --no -- commitlint --edit "$1"' > .husky/commit-msg

The local hook gives fast feedback. The CI commitlint job is what enforces the rule, because local hooks can be skipped.

Daily workflow

# 1. start from an up-to-date develop
git switch develop                   # or: git checkout develop
git pull --ff-only
git switch -c feature/jwks-rotation  # or: git checkout -b feature/jwks-rotation

# 2. work in small commits
git add -p
git commit -m "feat(auth): add JWKS endpoint"

# 3. before review: tidy history and catch up with develop
git fetch origin
git rebase -i origin/develop
git push -u origin feature/jwks-rotation --force-with-lease

# 4. open the PR (draft until CI is green and you have reviewed it yourself)
gh pr create --base develop --draft --fill

git switch vs git checkout

Both work. git checkout is the older command that does two jobs: it changes branches and it restores files. Git 2.23 split those jobs into git switch (branches only) and git restore (files only). This guide uses the newer commands because they are harder to misuse, but either set is fine.

TaskNewer (preferred)Older equivalent
Change to a branchgit switch developgit checkout develop
Create a branch and change to itgit switch -c feature/xgit checkout -b feature/x
Create a branch from a specific starting pointgit switch -c hotfix/x origin/maingit checkout -b hotfix/x origin/main
Go back to the previous branchgit switch -git checkout -
Look at a commit without a branch (detached HEAD)git switch --detach a1b2c3dgit checkout a1b2c3d
Discard local changes to a filegit restore file.tsgit checkout -- file.ts
Get a file as it is on another branchgit restore --source=main file.tsgit checkout main -- file.ts
Unstage a filegit restore --staged file.tsgit reset file.ts
Watch out with checkout: git checkout <name> looks for a branch first and then for a file. If a file has the same name as a branch, the command can silently throw away your uncommitted changes to that file. It also puts you in detached HEAD without warning when you give it a commit hash. switch and restore don't have either problem.

Aim for branches that live no longer than 5 working days. For longer work, merge it behind a feature flag in increments instead of keeping one long-lived branch.

Pull requests

  • Title uses the Conventional format, for example feat(auth): add JWKS rotation. Reviewers and the PR list read better that way.
  • Size: under 400 changed lines, not counting lockfiles and generated code. If a PR is bigger, split it into stacked PRs.
  • Draft until CI is green and you've read your own diff on GitHub.
  • Link the issue (Closes #123). For UI changes, add before and after screenshots.
  • Who merges: the author merges into develop once all checks pass. Only the release managers team merges into main.
  • Merged branches are deleted automatically.
.github/pull_request_template.md
## What
<!-- one or two sentences -->

## Why
<!-- problem / issue link: Closes #123 -->

## How to test
1.

## Checklist
- [ ] Commits follow Conventional Commits
- [ ] Tests added/updated; CI green
- [ ] No secrets, no debug logs, no commented-out code
- [ ] Docs / env.example updated if config changed
- [ ] Breaking change called out (and `!` in commit)

Expectations

  • Reviewers give a first response within 1 working day. Authors address feedback within 1 working day.
  • You can't approve your own PR. The approval must come from someone other than the person who pushed the last commit.
  • Prefix each comment so the author knows what is required: blocking: must change · suggestion: worth doing · question: needs an answer · nit: optional.
  • The person who opened a thread resolves it. Authors can resolve nit: threads after they fix them.
  • Review for correctness, security, tests, and readability. Formatting belongs to the linter, not to reviewers.

Branch protection

Set these up as GitHub Rulesets (Settings → Rules → Rulesets) rather than the legacy branch protection rules. Rulesets stack, and they can apply to every repo in the organization.

Why linear history is off: GitHub's "Require linear history" setting blocks merge commits, and merge commits are our merge strategy. Force-push and deletion are still blocked, so history on protected branches can't be rewritten.

Add a third ruleset for tags matching v*: block updates and deletions, and allow only the release bot to create them. Once a tag is published, it never changes.

Break-glass: the bypass list stays empty. In a real emergency, an org owner adds themselves temporarily, records the reason in #eng-incidents, and removes themselves straight after the fix. Every bypass gets a post-mortem.

CI/CD

TriggerRunsResult
PR into develop or maincommitlint, then verify (lint, typecheck, test, build)Status checks that block the merge
Merge into developBuild and deployStaging (staging environment)
Merge into mainrelease-pleaseOpens or updates the Release PR
Release PR mergedTag vX.Y.Z, GitHub Release, deployProduction (production environment, needs approval)

Rules

  • Required check names (the job names) must stay stable. If you rename a job, update the ruleset in the same PR, or every PR is blocked waiting for a check that never runs.
  • Never put continue-on-error on a required job, and never skip a test to get a PR green.
  • Flaky tests: fix them, or quarantine them with a linked issue within 1 working day. Re-running until it passes is not a fix.
  • Keep PR CI under 10 minutes. Cache dependencies and cancel superseded runs.
  • Keep deploy secrets in GitHub Environments, not as repo-level secrets. Use OIDC for cloud credentials instead of long-lived keys.
  • Workflows default to permissions: contents: read. Grant more per job only when it's needed.
.github/workflows/ci.yml
name: ci
on:
  pull_request:
    branches: [develop, main]

concurrency:
  group: ci-${{ github.head_ref }}
  cancel-in-progress: true

permissions:
  contents: read

jobs:
  commitlint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
        with: { fetch-depth: 0 }
      - uses: actions/setup-node@v5
        with: { node-version: 24, cache: npm }
      - run: npm ci
      - run: npx commitlint --from ${{ github.event.pull_request.base.sha }} --to ${{ github.event.pull_request.head.sha }} --verbose

  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-node@v5
        with: { node-version: 24, cache: npm }
      - run: npm ci
      - run: npm run lint
      - run: npm run typecheck
      - run: npm test
      - run: npm run build

For Python, .NET, or PHP repos, swap in the matching setup action and commands, but keep the job names commitlint and verify so one ruleset covers every repo.

Releases & hotfixes

Versions follow SemVer (vMAJOR.MINOR.PATCH). release-please calculates the version from commit types, writes CHANGELOG.md, and creates the tag and the GitHub Release. Nobody tags by hand.

Regular release

  1. QA signs off on staging.
  2. A release manager opens a PR from develop into main titled Release 2026-10-07.
  3. The PR needs 2 approvals and green CI, then merges with a merge commit.
  4. release-please opens a Release PR on main with the version bump and changelog. Review it and merge it (2 approvals).
  5. The tag vX.Y.Z and the GitHub Release are created, and the production deploy waits for production environment approval.
  6. Open a back-merge PR from main into develop (chore: back-merge main into develop) so develop gets the version bump.

Hotfix

  1. Run git fetch origin, then git switch -c hotfix/login-500 origin/main (or git checkout -b hotfix/login-500 origin/main).
  2. Fix the bug and add a regression test. Commit with fix(scope): ….
  3. Open a PR into main. It needs 2 approvals and green CI. Merge it.
  4. Merge the release-please patch Release PR. The tag (for example v1.4.1) triggers the production deploy.
  5. On the same day, open a back-merge PR from main into develop. A hotfix isn't finished until develop has it.
.github/workflows/release.yml
name: release
on:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  release-please:
    runs-on: ubuntu-latest
    outputs:
      released: ${{ steps.rp.outputs.release_created }}
      tag: ${{ steps.rp.outputs.tag_name }}
    steps:
      - uses: actions/create-github-app-token@v2
        id: app
        with:
          app-id: ${{ vars.RELEASE_APP_ID }}
          private-key: ${{ secrets.RELEASE_APP_KEY }}
      - uses: googleapis/release-please-action@v4
        id: rp
        with:
          token: ${{ steps.app.outputs.token }}
          release-type: node

  deploy-production:
    needs: release-please
    if: needs.release-please.outputs.released == 'true'
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@v5
        with: { ref: "${{ needs.release-please.outputs.tag }}" }
      - run: ./scripts/deploy.sh production
Use a GitHub App token, not the default GITHUB_TOKEN. PRs opened with GITHUB_TOKEN don't trigger workflows, so the Release PR would never get its required checks and could never merge. The app is also the only identity allowed to create v* tags.

Security & hygiene

  • Secret scanning and push protection are on for every repo. A push that contains a credential is blocked. Bypassing the block requires a reason, and every bypass is audited.
  • Never commit .env files or credential dumps. Commit a .env.example with placeholder values instead.
  • If a secret leaks: (1) revoke or rotate it immediately, (2) tell your lead, and (3) then purge it from history if needed. Rotating is the fix. Rewriting history is only cleanup, because clones and forks already have the secret.
  • Force-push and deletion are blocked on main, develop, and v* tags.
  • 2FA is mandatory for every organization member. Developers get Write access. Only leads get Maintain or Admin.
  • Never commit build output, node_modules, or binaries. Put files over 5 MB in Git LFS. GitHub rejects any file over 100 MB.
  • We're a mixed Windows, macOS, and Linux team, so normalise line endings with a .gitattributes file:
.gitattributes
* text=auto eol=lf
*.{cmd,bat,ps1} text eol=crlf
*.{png,jpg,gif,ico,pdf,woff2} binary

Housekeeping

  • develop must always be deployable. If it breaks, fixing it is everyone's top priority: revert first, then investigate.
  • Branches with no activity for more than 30 days get flagged. The owner deletes the branch or explains why it's still needed.
  • Never rewrite shared history. That includes main, develop, and any branch someone else has pulled.

Repo setup checklist

A repo admin does this once for each new repo.

Settings → General

  • Default branch: develop
  • Pull Requests: allow merge commits only (turn squash and rebase off)
  • Merge commit message: Default message, so release-please ignores merge commits and doesn't count features twice
  • Automatically delete head branches: on
  • Always suggest updating pull request branches: on

Rules & security

  • Rulesets for main, develop, and v* tags, configured as described in Branch protection
  • Secret scanning and push protection: on
  • Environments: staging (deploys from develop) and production (deploys from main and v* tags, with required reviewers)
  • Release GitHub App installed, with its ID in vars.RELEASE_APP_ID and its key in secrets.RELEASE_APP_KEY
